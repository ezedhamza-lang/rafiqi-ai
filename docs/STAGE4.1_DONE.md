## ما تم إنجازه

### 1. واجهة تجريدية للمزودين (Provider Interface)
- ملفات جديدة تحت `backend/src/services/payments/`:
  - `provider.js` — واجهة موحّدة + سجل المزودين (`getProvider` / `listProviders`) والتحقق من الاسم.
  - `demoProvider.js` — **المزود التجريبي DEMO**: يحاكي دورة دفع كاملة داخل المنصة دون أي بوابة خارجية (مناسب للمعاينة والاختبار).
  - `stripeProvider.js` — مزود **Stripe** الحقيقي (وضع اختبار sandbox): إنشاء Checkout Session عبر API، التحقق من توقيع الـ Webhook (`stripe-signature`) وترجمة أحداث Stripe.
  - `stbProvider.js` — مزود **البنك التونسي STB** (وضع اختبار): نقاط تكامل جاهزة تتطلب `STB_MERCHANT_ID` و `STB_SECRET`.
- كل مزود يطبق نفس العقد: `createCheckout` / `verifyWebhook` / `parseWebhook` / `info` — فيمكن إضافة مزود جديد أو التبديل بينهم دون أي كسر.

### 2. نماذج بيانات Prisma (تهجير جديد)
- `PaymentIntent` — نية الدفع: الاشتراك، المزوّد، الحالة (`PENDING` / `SUCCEEDED` / `FAILED` / `CANCELED` / `EXPIRED`)، المبلغ، العملة، مرجع المزود، رابط الدفع، رسالة الفشل، تواريخ الصلاحية/الدفع.
- `AuditLog` — سجل التدقيق الأمني: الفاعل، الدور، الحدث، المورد، عنوان IP، وكيل المتصفح، بيانات إضافية.
- تهجير `prisma/migrations/20260814231202_payments/migration.sql` (يُطبَّق عبر `prisma migrate deploy`).

### 3. مسارات API (`/api/payments`)
| المسار | الحماية | الوظيفة |
|---|---|---|
| `GET /api/payments/captcha` | عمومي | توليد تحدّي CAPTCHA (SVG حسابي) |
| `GET /api/payments/providers` | تسجيل دخول | قائمة المزودين وحالتهم (مضبوط/غير مضبوط) |
| `GET /api/payments/payable` | تسجيل دخول | اشتراكات المستخدم/الأبناء القابلة للدفع |
| `POST /api/payments/checkout` | ولي/إدارة + CAPTCHA | بدء عملية دفع ← إنشاء `PaymentIntent` ← رابط تحويل |
| `GET /api/payments/intents/mine` | تسجيل دخول | عمليات المستخدم |
| `GET /api/payments/intents/:id` | المالك/الإدارة | تفاصيل عملية |
| `POST /api/payments/intents/:id/cancel` | المالك/الإدارة | إلغاء عملية معلّقة |
| `GET /api/payments/demo-checkout/:intentId` | عمومي | صفحة دفع تجريبية (مزود DEMO) |
| `POST /api/payments/demo-checkout/:intentId/result` | عمومي | محاكاة نتيجة الدفع (نجاح/فشل/إلغاء) |
| `POST /api/payments/webhook/:provider` | توقيع Webhook | استقبال أحداث المزود وتحديث الاشتراك |
| `GET /api/payments/admin/intents` | إداري/نظامي | كل عمليات الدفع |
| `GET /api/payments/admin/audit-logs` | إداري/نظامي | سجلات التدقيق (تصفية حسب الحدث + ترقيم) |

### 4. معالجة الـ Webhooks (نجاح/فشل/إلغاء/انتهاء)
- `backend/src/services/paymentService.js` — `processWebhookEvent` يوحّد معالجة الأحداث من كل المزودين:
  - **SUCCEEDED** → تأشير النية ناجحة، تسجيل دفعة `Payment`، تفعيل الاشتراك والحساب وطلب الاشتراك، إشعار فوري للولي/التلميذ، سجل تدقيق.
  - **FAILED** → تأشير النية فاشلة مع سبب، إبقاء الاشتراك معلّقًا، سجل تدقيق.
  - **CANCELED / EXPIRED** → تأشير النية، سجل تدقيق.
  - **Idempotency**: تكرار نفس الـ Webhook لا يُحدث تأثيرًا مزدوجًا.
- البنية الخام للطلبات محفوظة (تُركَّب المسارات قبل `express.json`) للتحقق من توقيع Stripe.

### 5. التأمين: CAPTCHA + سجلات تدقيق
- `backend/src/services/captchaService.js` — CAPTCHA حسابي (جمع/ضرب) بتحدّي لمرة واحدة وصلاحية زمنية (`CAPTCHA_TTL_MS`)؛ `CAPTCHA_REVEAL_ANSWER=true` لإظهار الإجابة في الاختبار فقط (ممنوع في الإنتاج).
- `backend/src/services/auditService.js` + نموذج `AuditLog` — يسجّل كل حدث مالي (بدء الدفع، نجاح/فشل/إلغاء، Webhook مجهول/مكرر) مع IP ووكيل المتصفح، ويطّلع عليه الإداري/النظامي فقط.

### 6. الواجهة الأمامية (React)
- `frontend/src/pages/PaymentCenter.jsx` (تبويب «الدفع الإلكتروني» على الرابط `/payment`):
  - قائمة الاشتراكات المعلّقة للدفع (أبناء الولي + اشتراكه).
  - نافذة دفع: اختيار المزود + حل CAPTCHA (SVG) → توجيه لصفحة الدفع.
  - جدول عمليات الدفع السابقة بحالتها + إمكانية إلغاء المعلّق.
- ربط في `Header.jsx` (فضاءا الولي والأستاذ) و `App.jsx` (مسار `/payment`).
- صفحة الدفع التجريبية DEMO تُقدَّم من الخادم (`GET /api/payments/demo-checkout/:id`) بأزرار: إتمام بنجاح / محاكاة فشل / إلغاء — وكلها تمر عبر الـ Webhook نفسه.

### 7. اختبارات
- `backend/tests/payments.test.js` — 18 اختبارًا:
  - CAPTCHA: توليد، رفض إجابة خاطئة، رفض رمز منتهي.
  - Checkout: منع بدون تسجيل دخول، السماح للولي بدفع اشتراك ابنه، منع غير المالك، رفض دفع اشتراك مفعّل، `503` لمزود غير مضبوط.
  - Webhook: سيناريو النجاح الكامل (تفعيل + دفعة + إشعار + تدقيق)، الفشل، الإلغاء، التكرار (idempotent)، مزود غير معروف، توقيع Stripe غير صالح.
  - عمليات المستخدم وسجلات التدقيق: قائمة العمليات، إلغاء معلّق ثم منع الإلغاء المزدوج، سجلات التدقيق للإداري فقط، قائمة الاشتراكات القابلة للدفع.

## كيف تجرّب الدفع (وضع الاختبار)
1. سجّل الدخول كولي: `parent@test.tn / <كلمة-السر-تجريبية>`.
2. افتح «الدفع الإلكتروني» من فضاء الولي.
3. اختر اشتراكًا بانتظار الدفع ← «ادفع الآن» ← اختر «المزود التجريبي» ← حلّ رمز التحقق ← «المتابعة».
4. في صفحة الدفع التجريبية اضغط «إتمام الدفع بنجاح» → يُفعَّل الاشتراك فورًا وتصل إشعارات.
5. الإداري/النظامي يطّلع على العمليات وسجلات التدقيق عبر `GET /api/payments/admin/intents` و `GET /api/payments/admin/audit-logs`.
